# sbmlsim-web

The renderer of the interactive panels of an SBML model: Vue 3 components which draw a panel - its knobs, its curves and the study data under them - in any HTML page, a documentation site, a slide deck or a course.

A model declares its panels in its own SBML and an [sbmlsim](https://github.com/matthiaskoenig/sbmlsim) endpoint (`python -m sbmlsim.serve`) serves that declaration and runs its simulations. This library talks to such an endpoint and to nothing else, through three versioned JSON contracts:

| contract      | what it carries                                                 |
| ------------- | --------------------------------------------------------------- |
| `panel/1`     | the declaration of a panel and the answer of a simulation of it |
| `paneldata/1` | the study data drawn under its curves                           |
| `app/1`       | the pages of the panels of a model                              |

`src/contract.ts` is the only place which knows the shape of a payload. The ids of the models, panels, knobs, curves and series are data which come from those payloads, so no model and no entity of a model is built into this library, and `checkContract` refuses a payload of a version it does not speak.

A grid is fetched once per figure and not once per movement of a knob: `interpolate(grid, at)` reads a position between its points locally, multilinear over the axes and clamped to their ends. A point which did not integrate is `null` on the wire with its index in `status.failed`, and it gives `NaN` for the positions it bounds without touching a neighbour it does not bound.

`plotSvg(spec)` draws a figure as one inline SVG string: the axes with their ticks and their units, one path per curve, the study data as markers with error bars under them, whose shape is the position of a series among the ones of its curve, so two studies under one curve share its colour and are told apart by their markers, and a legend of up to ten curves or, above them, a colour bar, which is where sbmlsim draws one. It is pure - a string in, a string out, no dom, no canvas and no plotting library - so the same figure is built in a page, in a test and in a worker, and it stays crisp under the transform of a slide. The one thing it cannot know is how wide its text is drawn, since that is the font the page resolves: every width it lays out with - a tick label, the lines of an axis label, a legend entry, the rows of a legend and their centring, the column beside the plot - is asked of the `measure` of its spec, a function `(text, size) => pixels`. The element passes one built on canvas `measureText` in the font it draws its figure in (`canvasMeasure` of `fontOf` the panel), and lays its figure out once more when a font which was still loading has arrived; a spec without a measure is measured with the advance widths of Arial (`tableMeasure`), so a figure without a dom is still one exact figure. The sizes the text is drawn in are an input as well (`fontSizes`, the label and the small size): every width is measured at the size of its text and every line, row and margin is as tall as its font, so a page which sets `--sbmlsim-font-size` and `--sbmlsim-font-size-small` gets a figure laid out for them; the element passes the sizes those tokens resolve to. A logarithmic axis follows the rule of sbmlsim (at most six decades below the largest value), so a web figure and a matplotlib figure of the same data have the same limits. `plotGeometry(spec)` gives the layout that figure was drawn from - its plot box and the pixel of a value on either axis - so a caller which draws a crosshair, a readout or a marker of its own over a figure places it on the figure which is there and not on one it had to guess at. A figure takes the limits of its value axis from what it draws, or from the `yLimits` of its spec, which is what a caller passes which draws one of several lines of one answer at a time: a line then moves inside a frame which holds still instead of redrawing itself inside a frame which follows it, and the rule of the decades applies to that frame. A panel which declares the ends of its axes (`y_min`, `y_max`, `x_max`) gets them as `yEnds` and `xEnd`, which are no frame but the ends of the axis exactly: the axis runs from the one to the other with its ticks inside, so two states of the knobs are drawn against one axis, a curve or a point beyond them is cut at the plot box and drawn over no margin, legend or label, and study data beyond `xEnd` is no point of the figure; where one end is declared the other is derived as without, and on a logarithmic axis the ends are the ends of its decades, a declared end which is not positive being none there. A legend sits beside the plot or below it, packed into the rows of the figure, whichever of the two leaves the larger plot box: that is a column on a figure which is wide and short and a band of rows on the figure of a panel, and comparing the two is what keeps a figure which grows from ending up with a smaller plot than it had. A colour bar keeps its column either way. A figure of one curve and no study data, drawn or declared, has no legend, since its one entry would name the quantity its y label names; a figure of two or more curves, or with study data, keeps its legend and lays it out as before. The legend is laid out over the legends of `declaredLegends`, each the labels a state of the caller draws together in the order it declares them: the band keeps the rows of the legend which needs the most and the column the width of the widest label of any, and the figure draws the legend it has, so a figure keeps its plot box whichever of them is drawn and keeps the room of the largest legend one state draws, not of every series at once. A legend below the plot spans the plot box and centres its rows on it, as the label of the x axis above it is centred, so the plot, its label and its legend read as one block. The label of an axis wraps at its words onto two lines of the length of that axis rather than being cut, and the margins of a figure are grown by what its tick labels need beyond them, an x axis asks for fewer ticks where its measured labels would run into each other, always keeping its first and its last, every tick label starts on a whole pixel, at most half a pixel from where its tick centres it, so equal glyphs are drawn in one tint where a browser antialiases text by subpixels, and a layout which could draw its last tick alone, a number without a second one to read a scale from, is no candidate where the other layout draws both, so the label of the last tick stays inside the figure instead of being cut at its edge; that is `_fit_margins` of sbmlsim, so the two renderers answer a narrow figure the same way.

Every colour, font and stroke width of a figure is a `--sbmlsim-*` token whose fallback is the value of the style of the sbmlsim reports, so a page which loads nothing still gets the figure of a report. `src/theme.css` (`sbmlsim-web/theme.css`) carries those tokens in light and dark, and a page which sets one of them on the element it draws a panel in gets the figure in its own colours.

## The element

A page writes one tag and calls `activate()` on it:

```html
<script type="module" src="sbmlsim-web.js"></script>
<sbmlsim-panel
  endpoint="https://models.example.org"
  model="MODEL"
  panel="PANEL"
  fallback="./stored.json"
></sbmlsim-panel>
<script type="module">
  for (const one of document.querySelectorAll('sbmlsim-panel')) one.activate()
</script>
```

| attribute       | what it is                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `endpoint`      | the service the panel talks to; empty is the origin of the page, which is the teaching mode                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `model`         | the id of the model, as the endpoint serves it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `panel`         | the id of the panel of that model                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `variant`       | the variant of the model to simulate, which an app switches between; empty is the one the panel declares; a declaration may differ by the variant, so the panel reads its declaration and its study data in that variant, and a change starts it again: the declaration and the study data are read in the new variant, a knob of its own keeps a value the new declaration takes, and the figure of the variant before is held, dimmed, inert and hidden from a screen reader, with its provenance line, its head and its controls, which take no movement, so the panel keeps its height, until the first figure of the new one is drawn, or dropped at once when its run fails; a value of the host which is a bound or a choice of its knob to the last bits is sent as that number |
| `values`        | the knobs the page owns, a JSON object of knob id to number, e.g. `{"dose": 25}`: the panel sets them, draws no control of them and follows a change of the attribute as it follows a release of its own control; an id the panel does not declare is ignored, and text which is no such object, or a value which is no finite number, is one `console.warn` and leaves the panel as a panel which was never given the attribute: every control is drawn, and a knob the page owned is back at its default                                                                                                                                                                                                                                                                              |
| `head`          | the head the panel shows until it has read its declaration, a JSON object of its `title` and its `subtitle`, e.g. `{"title": "Plasma", "subtitle": ""}`; the shell of an app gives every panel the head the app names for it, so a card shows the head of the variant it is switched to at once, and a text which cannot be read is as if it were absent                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `layout`        | `auto` (the default, the controls beside the figure above 560 px and under it below), `sidebar`, `stacked`, `toolbar`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `theme`         | `auto` (the default, `prefers-color-scheme`), `light`, `dark`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `hover`         | `on` (the default, the crosshair and the readout at the cursor) or `off`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `data`          | `on` (the default, the study data of the panel under its curves) or `off`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `fallback`      | the url of a stored answer of a run, drawn when the endpoint does not answer; it has to be an answer of that panel at the knob values its declaration states, because the payload of an answer carries no knob state and the element therefore reads a stored one at those defaults                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `timeout`       | the milliseconds one request is given, 8000 without                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `heading-level` | the level the title of the panel is drawn at, 2 without; a page writes the level below its own heading here                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `auto`          | a boolean attribute: the element calls `activate()` itself when it is connected, which is what a page with one panel and no script of its own needs; without it nothing is drawn and nothing is requested before `activate()`, because a deck has every slide in the page; the attribute counts by its presence, so `auto="false"` also starts the element, it is read when the element is connected, so adding it afterwards does nothing, and an element which is removed and connected again starts again with fresh requests                                                                                                                                                                                                                                                        |

`activate()` starts it, `freeze()` stops every pending request and freezes the knobs, and `reset()` puts the knobs back to the values the declaration states. Nothing is fetched and nothing is drawn before `activate()`, so a slide deck or a long page mounts its panels lazily. The element registers itself on import under `sbmlsim-panel`; `register(tagName)` gives it another tag.

**A request grids over at most one knob.** The first run grids over the first `range` knob of the panel at its declared `steps`, with every other knob at its default, and while that knob moves every movement is read out of the grid locally: five moves of it are no request at all. Releasing any other knob schedules one run which grids over **that** knob instead and holds the one which was gridded before at the value it now has, so the knob a reader is working with is always the one which costs nothing. An `input` event interpolates and redraws, a `change` event schedules a run, and a scheduled run which is superseded is cancelled rather than raced. The knob which counts as the gridded one is the knob the run which is scheduled or in flight grids over and not the one the last answer gridded over, so a knob released while a run is on its way gets a run of its own instead of a figure which contradicts it.

**A range knob may name stops on its slider.** A knob of the kind `range` whose `choices` name values inside its bounds - the stages of a renal impairment over a creatinine clearance - draws a select of those stops above its slider, under the one label of the knob: the label names the slider, the select is named by the label and the words `named value`, and both take the keyboard. Picking a stop moves the slider to it and draws the panel there, the slider tells a screen reader the stop it is at (`aria-valuetext` such as `110, normal`), a slider moved onto a stop shows that stop in the select, and a value which is no stop shows the entry `custom`, which is drawn only then and cannot be picked. The slider moves on a ladder which reaches every stop. A range knob without stops is drawn as before, and a knob is the same control in a panel and above the grid of an app. A knob of a dimensionless unit (`dimensionless`, `1`) has its label alone, as a number of no unit. A row of controls - the controls of a panel above or below its figure and the shared controls of an app - is a grid whose items each take two rows of their line, the line of the labels and the line of the bodies, so the options of a panel and the Reset of the shell sit on the line of the selects beside knobs and at the top of a line of their own, whatever wraps where and whatever font the page draws in, and the Reset of the shell takes a column of its own and never width from a control. The shared controls of an app have as many columns as fit at 200 px, which share the width of their card, so the card is filled from edge to edge; where it holds two columns or more, the Reset sits beside the select of the examples of the page, level with it, and in one column it takes a line of its own under the knobs. While a panel has no declaration to draw - before it read its first one, and while it reads the one of the variant a reader switched to - its options, the logarithmic y and the Reset, are disabled with its knobs, since the declaration it reads sets the axis it declares. A knob without a `target` is one the derived values of the simulation read: it is drawn and sent as any other, and the element reads no target.

**The readout is a view of the drawn grid.** A pointer over the figure draws a crosshair at the nearest x of the grid and a box which reads out every curve there, with the colour of the curve, its label and its value with its unit. It costs no request and no interpolation of its own: it shows what the figure already shows. The box never leaves the plot box - it flips to the other side of the crosshair where it would pass the right edge and is clamped at the top and the bottom - and it is laid out on the geometry the renderer drew from (`plotGeometry(spec)`), so it sits on the figure which is there. A plot box too short for one row per curve gets the rows it has room for and a last row reading `+N more`, as a legend label too long for its column ends in an ellipsis; the markers on the crosshair are drawn for every curve whatever the box shows. It follows `pointermove`, so a pen and a finger read a panel as a mouse does, and a device which never moves a pointer simply has no readout. For a screen reader the crosshair and the readout are decoration (`aria-hidden`); the figure keeps its `role="img"` and its `<title>` and takes no focus. `hover="off"` leaves all of it out.

**The study data is one fetch per declaration.** A panel which declares study data reads `paneldata/1` once, when it is activated or reads its declaration again for another variant, model or panel, and draws it as markers with error bars under its curves; it depends on no knob, so it is never read again. The series arrive in the unit the model resolved for the curve they sit under, so nothing is converted in the page; a series which is delivered on a scale of its own is left out, because a figure has one y axis, and three things put it there: it sits under a curve the panel does not draw, e.g. a declaration which names one by a typo, its values are in another unit than that curve, or its x is in another unit than the run. Such a series is no failure of the panel, so it is no error line and no `sbmlsim-error`; the element writes one `console.warn` for it, once per series, which names the series, the curve it sits under and the two units, because the one who can fix a declaration or a study is the one reading the console. A study measures what it measured and a panel simulates the horizon it declares: a point beyond the x of the curves is no point of the figure, it stretches neither axis and draws nothing outside the plot box. A series which declares the state of the knobs it was measured under (`at`) is drawn only while the figure is at that state, so a panel never shows the data of one condition under a curve of another; a knob the state does not name is not constrained, and the state which is compared is the one the drawn answer was run at and never the one the controls are in, since a control changes at once while the figure follows a round trip later. The knob the drawn answer grids over is the exception and needs none: the figure reads a movement of it out of the grid, so its curve and its series move together with the control, and every other knob brings its series back with the answer of its value, so the two halves of the figure are always of one condition. That is no mistake in a declaration, so nothing is written about it. A failed fetch of the study data is no failure of the panel: the curves stay, the overlay is absent, no line is written and no `sbmlsim-error` is dispatched, because nothing a reader asked for failed. `data="off"` asks for none of it.

**Nothing rejects into the page.** A dead network, a slow endpoint, a refused request, a payload of another contract version and a body which cannot be read are all caught inside the element, retried once where that can help, and resolved into the stored result and one line a reader can act on. The line names no url and no host. A failure is no freeze: the knobs keep working and the next move of any knob runs again. Until a run answers, the figure is drawn only while it is of the state the knobs and the `variant` show; where a knob or the variant stands elsewhere the panel draws no figure, no provenance footer, and its line says that the figure of the settings shown cannot be drawn, so a panel never shows a state no control shows. A change of `endpoint`, `model` or `panel` after the panel started starts it again with what they name. `freeze()` is the one stop of a panel. Reset acts while it changes something, a knob of the panel away from its default or the scale of the y axis; while it would change nothing it says so (`aria-disabled`) and ignores a press, but keeps the focus a keyboard reader pressed it with. The element also dispatches `sbmlsim-error` (`{detail: {kind, message}}`, bubbling and composed) so a page can react. The stored result is fetched on `activate()` next to the declaration and not when a request fails, because an endpoint which cannot be reached cannot serve a fallback either. A stored result has to be an answer of the panel at the knob values its declaration states: the payload of an answer carries no knob state, so the element reads it at those defaults and cannot notice one which was computed at another state.

The element has a shadow root, so the styles of the host page cannot reach it and it cannot leak into the page; the `--sbmlsim-*` tokens are the one hook from outside, and they work from the element and from anything above it. The element declares no token of its own on its host: it reads every one of them into a private token with the value of the design as the fallback, so a documentation theme, the dark switch of a slide deck or a branded container which sets `--sbmlsim-accent` on a wrapper is what the panel takes. A rule of the page which matches the element itself wins over all of it, `theme="light"` and `theme="dark"` come next as the explicit opt-in they are, then an ancestor, then `prefers-color-scheme`, then the table of `theme.css`. Nothing of the typography and nothing of the colour of the panel is declared on the host either, because a declaration of the page which matches the element, `* { font-family: ... }` among them, beats one of the shadow tree there and everything in the panel would inherit it.

## The app shell

`<sbmlsim-app>` is the shell of the app of a model, which replaces a webapp written by hand per model. A page writes one script tag and one element tag, and the model's own declaration (`app/1`, `Project.app` of sbmlsim) is the rest:

```html
<script src="sbmlsim-web.iife.js"></script>
<sbmlsim-app endpoint="https://models.example.org" model="MODEL"></sbmlsim-app>
```

| attribute       | what it is                                                                                                                        |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `endpoint`      | the service the app talks to; empty is the origin of the page                                                                     |
| `model`         | the id of the model, as the endpoint serves it                                                                                    |
| `page`          | the id of the page which is shown, the first page without or for an unknown id; the shell sets it when a reader switches the page |
| `theme`         | `auto` (the default), `light`, `dark`, passed to every panel                                                                      |
| `timeout`       | the milliseconds one request is given, 8000 without                                                                               |
| `heading-level` | the level the title of the app is drawn at, 1 without; its panels are drawn one level below it                                    |

It draws the title and the subtitle, the navigation of the pages (none for an app of one page), the switcher of the variants (none for an app of fewer than two), the grid of the panels of the page and the provenance footer: the citation, the DOI and the licenses of the declaration and the versions which simulated what is shown, which it reads from the `sbmlsim-result` events of its panels. The grid has as many columns as fit panels of at least 30rem of the width of the shell, so it is one column below about 976 px of that width and two above, a lone panel takes the row, and an app in a column of a page is as narrow as its column. The cards of a row share the rows of the grid: the head, the body and the foot of their panels are laid out as subgrids of them through the part `panel` a panel exposes (the parts `figure` and `foot`, its figure and its provenance line, are what the shell dims during a switch of the variant), so the plots of a row line up whatever the lines of their titles and whatever sits under them; a panel alone in a page is laid out as it always is. The rows of a card are reserved before its panel has read anything: the app names the title and the subtitle of every panel of a page (`heads`), the shell lays out a copy of the head of each panel in its card, in the type of the head of the panel and at the width of the card and never shown, so the head row of a row of cards is as tall as its tallest head on the first frame, a panel reserves the height of its figure from its width, and the foot row holds one line of provenance, so a card does not move under the reader while the panels load. The shell paints its own surface, dark under `theme="dark"` and under a dark colour scheme, and its text is read against it and not against the page. The shell owns no simulation logic: it reads `app/1`, once per variant a reader chooses, and nothing else, and never simulates; a panel is an `<sbmlsim-panel auto>` which does its own work.

**A knob the panels of a page share is one control.** A knob id which more than one panel of the page declares is drawn once, above the grid, with the control a panel draws, and no panel of the page draws one of it; every panel which declares it gets the attribute `values` with the shared knobs it declares and follows the control, so every plot of the page is of the state the controls show, and a panel whose run failed says it cannot draw that state rather than draw another. A knob id one panel declares stays in that panel, and a panel which declares no shared knob gets no `values` and makes no request when one moves. The service states the shared knobs of each page in the app (`shared`), next to the heads of its panels, and refuses an app whose page declares one knob id differently on two panels, so the shell reads no declaration of a panel and a panel which cannot be read changes nothing of the controls of its page. The shared controls have a Reset of their own, and a screen reader hears the titles of the panels a control sets. A panel embedded alone draws every control it declares.

**A page may name scenarios of its knobs.** A page whose `scenarios` name states of its shared knobs - example patients - draws a select of them, labelled `Example`, above the controls they set. Picking one sets every knob it names in one state, so a panel runs at most once for it however many of its knobs moved, and leaves every knob it does not name where it is. The select shows the first scenario whose every value is the value its knob has, else the entry `custom`, which is drawn only then and cannot be picked; Reset puts the knobs back to their defaults and the select follows. A page without scenarios draws nothing of them.

**A page change swaps the panels in the grid.** The panels of the page which is left are frozen and removed, and the panels of the page which is shown start themselves, so the DOM holds the panels of one page. A panel is created again when its page is returned to, with its knobs and the shared knobs of the page at the values of their declaration, and the endpoint answers its first grid from its cache.

**The app follows the variant.** The declarations of the panels may differ by the variant of the model, and so may the knobs a page shares, its scenarios and the heads of its cards: a switch of the variant reads the app again in it (`?variant=`), and the app names the variant it answers (`variant`), which the shell checks against the one it asked for and keeps, so the app of every variant, the first one included, is read once. While the app is read, the panels keep the figures of the variant before, dimmed, inert and hidden from a screen reader (`inert`, `aria-hidden`), with a caption beside the switcher which names the variant they are switched to ("Switching to ... …", whose room, that of the longest caption of any variant, is kept at all times), the provenance line of their answers stays as well, dimmed as they are, the shared controls and the tabs take no movement, and nothing of the page moves. When it arrives the controls, the scenarios and the heads are of that variant, a shared knob keeps its value where it is a knob of that variant which takes it and starts at its default otherwise, and the panels get the variant and those values at once; each holds its figure of the variant before, dimmed, until it draws one of the new variant, and the caption and the dimmed provenance line stay until every panel of the page has drawn or failed; the answer of a panel which failed is dropped from the line as its figure is. An app of a variant which cannot be read leaves no figure of the variant before (the panels keep their room and are not drawn) and a line which says so, and switching back to the variant which was drawn draws it again without a request.

**The chosen variant goes to every panel.** It is the `variant` attribute of the panels, which send it in the body of the simulation, and it stays chosen while the page changes.

**A failure leaves one line.** An app which cannot be read - an endpoint which is down, a model without an app, a payload of another version - shows one line in the voice of the panel, which names no url, no host and no status, and no navigation, grid or footer; `sbmlsim-error` is dispatched as a panel does.

A panel dispatches `sbmlsim-result` with the `provenance` and the `spec_hash` of every successful simulation, never of a failure and never of a stored fallback. The shell dispatches `sbmlsim-page` with `detail.page`, the id of the page, when a reader switches the page (not when a page sets the attribute itself), which lets a deployment give its pages addresses and answer the back button by setting `page` again, and it announces the switch to a screen reader in a polite live region. `register(tagName, appTagName)` gives either element another tag, and the shells place their panels under `tagName`.

## Build

```bash
npm ci
npm run lint       # eslint and prettier
npm test           # vitest
npm run typecheck  # the whole project, the tests included
npm run build      # dist/sbmlsim-web.js (ESM), .umd.cjs (UMD), .iife.js (IIFE), dist/types
npm run e2e        # the demo pages in Chrome against a live endpoint, see below
npm run format     # write what prettier wants
```

Vue is bundled into every build, so a host page needs nothing else: it reads `dist/sbmlsim-web.js` with a `<script type="module">` or through a bundler, `dist/sbmlsim-web.umd.cjs` is the same library for a `require`, and `dist/sbmlsim-web.iife.js` is the one for a page which wants the `sbmlsimWeb` global from a plain `<script src>`, which a static server serves as a script where it serves a `.cjs` file as a download.

## The demo pages and the end to end tests

`demo/` has the four pages the elements are tested on, the three hosts of the panel and the page of an app: `plain.html` (one script tag and one element tag, the page of a course platform), `slides.html` (reveal.js on a dark theme, which activates a panel when its slide is shown and freezes it when it is left) and `docs.md` (a raw HTML block in a markdown page, which `scripts/stage-demo.mjs` renders to `docs.html` for the tests), and `app.html` is the page a model deployment serves: one script tag and one `<sbmlsim-app>` tag. `npm run e2e` stages them and serves them with the endpoint of the python package, `python -m sbmlsim.serve --static`, so a page and its API are one origin, and drives the installed Chrome through playwright. The endpoint is the checkout in `SBMLSIM_REPO` (`../sbmlsim` without), serving `examples.panels.hctz:PROJECT`; where there is no such checkout the command says that it skipped and exits 0.
